# Literature-to-Design Matrix

**Status:** Day 1 working version
**Decision use:** design justification and claim control, not a source of pre-written
simulation results
**System in scope:** a traveller-level, two-stage `Security -> Immigration`
checkpoint model with finite resources, queue-policy alternatives, automation
scenarios, and exception checks

## 1. Evidence rules

This review uses peer-reviewed papers, Winter Simulation Conference tutorials,
and official ICA/HTX publications. A citation earns a place here only when it
changes a design decision, a test, or the boundary of a final claim.

Four evidence classes must remain separate:

1. **Local measurement:** the supplied video's audited crossing events.
2. **Model assumption:** a transparent simplification required to make the DES
   executable, such as a candidate arrival-process family.
3. **Literature-supported mechanism:** a relationship worth representing or
   testing, such as finite-resource queues or secondary checks.
4. **Official context:** evidence that an intervention is operationally relevant,
   not a calibration value for this local model.

No ICA-wide annual volume, national checkpoint total, or airport-wide clearance
figure may be divided by time and used as the arrival rate for the local video
corridor. No literature result below is a substitute for a measured local service
time, routing probability, counter roster, or queue layout.

## 2. Matrix A — model scope and queue design

| ID | Literature proposition and source | Design decision in this project | Testable implementation / delivery evidence | Maximum defensible claim |
|---|---|---|---|---|
| M1 | Discrete-event simulation represents a system through events, states, entities, resources, and queues; simulation is experimentation with a purpose-built model. [Ingalls & White, *The Basics of Simulation* (2016)](https://informs-sim.org/wsc16papers/007.pdf) | Use a true event calendar for arrivals, queue entry, service start, service completion, and exception completion. Model each traveller as an entity and Security/Immigration capacity as constrained resources. Do not advance operations with animation frames. | Event log contains ordered timestamps and resource IDs. Invariants: no service starts before arrival; no resource occupancy exceeds capacity; all state changes occur at declared events. A deterministic hand-worked trace must reproduce exactly. | “This is an event-driven DES of the specified two-stage process.” It is not a pedestrian-flow or digital-twin claim. |
| M2 | A conceptual model should be software-independent and state objectives, inputs, outputs, content, assumptions, and simplifications; the right abstraction is the simplest one that remains valid, credible, useful, and feasible for its purpose. [Robinson, *A Tutorial on Simulation Conceptual Modeling* (2017)](https://informs-sim.org/wsc17papers/includes/files/041.pdf) | Let the research question select DES and then the engine, not vice versa. Include only mechanisms needed for capacity, queue policy, automation, and exceptions. Keep walking animation explanatory because no spatial-behaviour data calibrate an ABM or pedestrian model. | Task 2 names the objective, boundary, entities, events, inputs, outputs, assumptions, and exclusions before implementation. The same input/output contract remains valid if AnyLogic is replaced by the fallback engine. | “DES is appropriate for the decision question under the stated abstraction.” Do not claim that engine choice itself adds scientific validity or that the 2D animation predicts physical crowd motion. |
| M3 | A checkpoint DES can connect arrivals, finite screening capacity, alarms/secondary inspection, throughput, and cycle time; in the cited airport case, the authors verified and validated before sensitivity analysis. [Dorton & Liu, *Human Factors and Ergonomics in Manufacturing & Service Industries* (2016)](https://doi.org/10.1002/hfm.20616) | Represent Security and Immigration as separate constrained stages and represent additional immigration checks explicitly, rather than hiding them inside an average service time. Treat exception probability and duration as scenario inputs until local evidence exists. | Unit tests force exception probability to `0` and `1`; conservation checks reconcile primary and exception flows; sensitivity output records exception count, stage waits, total wait, and cohort clear time. | “Secondary checks are an explicit, testable bottleneck mechanism.” The cited airport-security case does not calibrate Singapore immigration parameters or prove the direction/magnitude of our results. |
| Q1 | Pooling can improve resource use, but its value is not universal: complete or partial pooling can help or hurt depending on the network and service structure. [Mandelbaum & Reiman, *Management Science* (1998)](https://doi.org/10.1287/mnsc.44.7.971) | Implement `separate` and `pooled` as genuinely different routing mechanisms while holding counter count, traveller demand, service requirements, run horizon, and initial state fixed. | Mechanism test: pooled has one FCFS queue feeding all eligible counters; separate has counter-specific queues with a frozen routing/tie rule. A configuration diff proves that no capacity or demand input changed. | “Pooling changed performance in this model under these assumptions.” Do not call pooling inherently superior or infer the site's current queue rule. |
| Q2 | Even when pooling reduces server idleness, a dedicated-queue design with join-the-shortest-queue routing can perform better on some delay-target measures in the paper's large-scale, moderately overloaded setting. [Cao, He, Huang & Liu, *Operations Research* (2020)](https://doi.org/10.1287/opre.2019.1976) | Pre-specify both mean and tail/service-level outcomes; do not use capacity utilisation alone to rank queue designs. If separate queues use shortest-queue routing, state that rule and its information assumption. | Report the same KPI set for both mechanisms: replication-level tail wait, threshold exceedance, mean wait, utilisation, imbalance, cutoff backlog, and clear time. | A tail-KPI result may differ from a mean or utilisation result. The cited asymptotic setting is motivation for testing, not a prediction of which design will win here. |
| Q3 | Pooling results are sensitive to heterogeneity; the theoretical literature contains cases in which pooling gains reverse or become unbounded in either direction. Delay-target optimisation can also create excessive waits for non-prioritised customers. [Mandelbaum & Reiman (1998)](https://doi.org/10.1287/mnsc.44.7.971); [Legros, *Operations Research Letters* (2016)](https://doi.org/10.1016/j.orl.2016.10.011) | The primary queue-policy comparison uses explicitly homogeneous counters. Add a bounded exploratory sensitivity for counter-speed or traveller-class heterogeneity only if it is implemented cleanly. Keep mean, extreme-wait/exceedance, and subgroup guardrails beside P95. | Configuration records whether counter and traveller heterogeneity are enabled. Results are stratified by traveller/route class when relevant; no group is hidden inside an aggregate service-level statistic. | A homogeneous-counter pooling finding applies only to that model. Without local counter-level or class-level data, heterogeneity analysis is a structural sensitivity, not a calibrated operational conclusion. |

## 3. Matrix B — estimands, replications, and input uncertainty

| ID | Literature proposition and source | Design decision in this project | Testable implementation / delivery evidence | Maximum defensible claim |
|---|---|---|---|---|
| S1 | One stochastic run is one realisation, not “the answer.” For a terminating system, independent replications begin from the same initial condition, reset statistics, and use different random numbers; independence across replications enables ordinary output analysis. [Law, *Statistical Analysis of Simulation Output Data: The Practical State of the Art* (2020)](https://informs-sim.org/wsc20papers/134.pdf) | Treat the operational period as a terminating arrival cohort: admit travellers until the cutoff, stop new arrivals, then drain the cohort. Compute every KPI once per replication and use replication-level values as the statistical sample. | Each output row contains `scenario_id`, `input_sample_id`, `replication_id`, and seed lineage. Re-running a manifest is identical; changing the replication seed changes stochastic draws. `arrivals = completed_at_cutoff + WIP_at_cutoff` and `arrivals = completed_after_drain`. | Report an estimate and uncertainty interval over model replications. Never present one animated run, or thousands of correlated traveller rows, as thousands of independent experiments. |
| S2 | Averages alone can conceal service risk, and queue structures can rank differently for a delay target than for utilisation or mean wait. [Cao et al. (2020)](https://doi.org/10.1287/opre.2019.1976). Percentile-defined service levels can also create undesirable extremes if optimised in isolation. [Legros (2016)](https://doi.org/10.1016/j.orl.2016.10.011) | Define `Q95_r` as the P95 total waiting time among the pre-specified arrival cohort in replication `r`. The primary estimand is the mean of `Q95_r` across replications with a CI; it is not the P95 of all pooled traveller rows. Pair it with exceedance probability, mean wait, maximum/upper-tail diagnostics, backlog, throughput at cutoff, and clear time. | KPI code is tested on synthetic cohorts with known quantiles. The analysis script can reproduce `Q95_r` from entity logs and shows the cohort denominator. The service threshold and confirmatory decision rule are frozen before confirmatory runs. | “Within the tested scenarios, the modelled distribution of daily/cohort tail waiting changed by …” after results exist. Do not claim that P95 alone proves fairness, safety, or operational acceptability. |
| S3 | Multiple independent streams/substreams support both independent replications and synchronisation across alternatives. [L'Ecuyer, Simard, Chen & Kelton, *Operations Research* (2002)](https://doi.org/10.1287/opre.50.6.1073.358). CRN reduces variance only under a properly synchronised comparison. [Chen, Winter Simulation Conference (2001)](https://informs-sim.org/wsc01papers/053.PDF) | Pre-generate a traveller-level input ledger or use named streams for arrival, class, Security service, Immigration service, exception, and automation outcome. Use the same exogenous traveller inputs across policy alternatives. A shared top-level seed alone does not qualify as CRN. | An alignment test compares traveller IDs and their exogenous draws across scenarios. Branch-specific draws are assigned by event/entity identity or sampled in advance so a policy branch cannot shift all downstream draws. Store a seed manifest. | Use paired differences and paired CIs only after alignment and positive/useful pairing are verified. Otherwise label the comparison independent and use an independent two-sample difference CI. |
| S4 | Finite real-world samples create input-model error in addition to Monte Carlo error; ignoring that distinction can materially change output characterisation. [Barton, *Tutorial: Input Uncertainty in Output Analysis* (2012)](https://informs-sim.org/wsc12papers/includes/files/inv209.pdf) | Separate inner stochastic replications from outer arrival-input samples. Propagate video measurement uncertainty for finalists if the engine workflow passes its gate; otherwise run a declared `lower/base/upper` input sensitivity plus an arrival-family sensitivity. | Output includes both `input_sample_id` and `replication_id`. The analysis decomposes, or at minimum visibly separates, variation across input samples from variation across replications. | A result is conditional on the declared input-uncertainty model and tested range. A narrow Monte Carlo CI does not mean the local arrival input is known precisely. |
| S5 | Input modelling seeks an approximation that preserves important features; there is no automatically “true” standard family. Arrival processes may be dependent or change over time, for which stationary textbook models can fail. [Biller & Gunes, *Introduction to Simulation Input Modeling* (2010)](https://informs-sim.org/wsc10papers/006.pdf) | The short clip first yields an audited event trace. Compare only parsimonious candidates that the sample can support: trace replay for debugging, a homogeneous-Poisson count model as an explicit stationarity/independence assumption, and a simple empirical/renewal alternative only if event count and diagnostics permit. Do not fit an NHPP, mixture, or time-of-day profile to one short window. | Preserve event timestamps, direction, audit status, ROI/line geometry, and source hash. Show count/inter-arrival diagnostics and a model-choice note. Run arrival-family and rate sensitivity rather than selecting by an unqualified goodness-of-fit p-value. | The video can support a local, time-bounded crossing trace and assumption-conditioned scenarios. It cannot establish a long-run peak, daily seasonality, checkpoint-wide arrival process, or a unique inter-arrival distribution. |
| S6 | A fixed replication count such as 30 is not intrinsically sufficient; precision depends on output variance and the required interval width. Law's output-analysis tutorial treats replication count, run length, and warm-up/initial conditions as study-design choices. [Law (2020)](https://informs-sim.org/wsc20papers/134.pdf) | Use independent pilot seeds to estimate variance, choose a fixed confirmatory `N` from a predeclared absolute/relative half-width target and run cap, then freeze `N` before inspecting confirmatory decisions. | The analysis plan records pilot IDs, precision target, formula/rule, final `N`, run cap, and untouched confirmatory seed manifest. If precision is not achieved at the cap, report achieved half-width. | The CI describes the frozen design. Do not extend runs after seeing an inconvenient result or describe “30 runs” as a universal adequacy guarantee. |

## 5. Pre-result design commitments

The following decisions should be frozen before confirmatory simulation results are
inspected:

1. the operational meaning of each video direction and the final signed-off crossing
   ledger;
2. the baseline arrival model, competing arrival-family sensitivity, and input-
   uncertainty method;
3. the terminating arrival cohort, cutoff, drain rule, KPI definitions, service
   threshold, and guardrails;
4. the exact mechanism and routing/tie rule for separate versus pooled queues;
5. whether counters are homogeneous in the primary comparison and which
   heterogeneity sensitivity, if any, is allowed;
6. automation mapping, effective-uptake definition, exception logic, and the labels
   attached to the official `0.6` and `0.4` contextual anchors;
7. random-stream/ledger design, CRN alignment test, pilot precision target,
   confirmatory replication count, and seed manifest; and
8. the V&V acceptance checklist and unresolved operational-validation gaps.

No row in this document predicts that capacity, pooling, or automation will be best.
Those are hypotheses to be tested. The strongest eventual statement is a bounded
one: **under documented model assumptions and over the tested scenario/input range,
an intervention changed specified model KPIs by an estimated amount and uncertainty
interval.**

## 6. Claim ladder for the final report

| Level | Permitted wording | Evidence required |
|---|---|---|
| Local measurement | “Within the defined video ROI, line, direction convention, and observation window, the signed-off audit contains … crossings.” | Reproducible detector/tracker manifest, complete event audit, false-negative sweep, sensitivity summary |
| Computer-model result | “Under configuration X, the DES estimates …” | Passing verification, replication-level output, uncertainty interval, full provenance |
| Comparative result | “Changing only policy/capacity factor X changed model KPI Y by …” | Controlled config diff; CRN alignment and paired CI, or an honestly independent difference CI |
| Robustness result | “The decision remained unchanged over the tested input/scenario range.” | Predeclared range, input uncertainty/sensitivity, decision rule, no untested extrapolation |
| Operational recommendation | Not currently available | Local service/routing/resource/output data, stakeholder face validation, and operational validation over the intended domain |
